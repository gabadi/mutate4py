# Performance report — full `src/` mutation gate, 2026-08-06 (corrected)

Supersedes an earlier draft of this file that claimed "12 redundant
per-file baselines" cost ~683s. That claim was never verified and turned
out to be **wrong** — source reading (`_prepare_directory_baseline`,
`_resolve_baseline_duration`) and empirical tracking (below) both confirm
the baseline runs exactly **once** per directory sweep, not once per file.
This version replaces it with a verified breakdown and a shipped fix.

## Ground truth: where ~1701s actually went

A full `src/` sweep (346 sites, 12 files) was run with every real `pytest`
invocation logged (timestamp + args) via a `--test-command` wrapper. 302
real invocations occurred: 1 directory-level baseline + 301 per-mutant runs
(matches Killed+Survived = 301; the other 45 sites are Uncovered and are
skipped — no test run at all).

| Invocation type | Count | Total time | Avg |
|---|---|---|---|
| Baseline + full-suite fallback (empty `--test-contexts` match) | 8 | ~100s | 12.6s |
| Scoped (`--test-contexts`-narrowed, 1-8 node IDs) | 293 | ~1652s | 5.64s |

The baseline is cheap and single — the old "12 baselines" theory is dead.
**The dominant cost is the 293 scoped invocations**, at ~5.6s each. A bare
scoped pytest subprocess (1-2 tests) runs in ~1-2s wall time measured in
isolation, so roughly 3.5-4.5s of each mutant's cost is **mutate4py's own
per-mutant orchestration** — writing the mutated source, invoking the test
subprocess, restoring the original source, and manifest bookkeeping — not
purely fresh-interpreter startup. Interpreter startup is a real component
of the cost but not the majority of it. This is flagged, not fixed, per
scope below.

## Root cause found and fixed: integration tests in the mutation test command

`tests/test_main.py` contained 52 tests that spawn a **second, fresh Python
interpreter** via `subprocess.run([sys.executable, "-m", "mutate4py", ...])`
(47 via `_run_cli_path`/`_run_cli_in` helpers, 5 inlined directly). These
are genuine CLI integration tests, not unit tests, and the mutation gate's
`--test-command` defaulted to bare `pytest` — meaning every baseline run
and every full-suite-fallback mutant paid for all 52 of them.

Verified before applying any fix: **0 of 346 mutation sites depend on an
integration test for coverage** — `pytest-cov`'s `--cov-context=test` only
records coverage for code that runs in-process; it cannot see inside a
spawned subprocess, so integration tests never appear in any mutant's
per-mutant test-selection scoping (confirmed via `TestContextDB.tests_for_line`
cross-referenced against every site, including the 8 empty-args/fallback
invocations). Excluding them from the mutation gate costs zero kill
coverage.

### Fix shipped

- `tests/test_main.py`: all 52 subprocess-spawning tests marked
  `@pytest.mark.integration`.
- `pyproject.toml`: registered the `integration` marker, added
  `--strict-markers`.
- `justfile`'s `mutate` recipe: now defaults `--test-command` to
  `pytest -m "not integration"` (overridable via recipe args). Does not
  affect `--scan`/`--check-manifest`, which bypass this recipe entirely.
- `tests/test_integration_marker_guard.py`: new guardrail meta-test. Scans
  every test file's AST for test functions that spawn a subprocess with
  `sys.executable` (or call the known `_run_cli_path`/`_run_cli_in`
  helpers) without the `integration` marker, and fails if any are found.
  This is what caught the 5 tests that used inline `subprocess.run(...)`
  instead of the helpers and were missed by an initial manual `grep`.

### Verified result

Full `src/` sweep, same 346 sites, rerun after the fix:

| | Before | After | Δ |
|---|---|---|---|
| Wall time | ~1701s (untracked) / 1756s (tracked) | **1103s** | **-35% / -37%** |
| Killed | 207-208 | 208 | parity (±1 flaky borderline mutant, unrelated to this change) |
| Survived | 93-94 | 93 | parity |
| Uncovered | 45 | 45 | exact match |

No mutants gained or lost coverage. The full `test` gate (`just check test`
/ `just test`) still runs all 687 tests including the 52 integration ones —
only the mutation gate's test command changed.

## What this branch's changes bought overall

- Issue 02 (`check.sh` → `justfile` + `--test-contexts` wiring): CI-facing
  sample gate (`_cmd.py`, 4 sites) 147.7s → ~24-30s (~5-6x).
- This fix (integration-test exclusion from the mutation test command):
  full `src/` sweep 1701s → 1103s (~35% faster), zero kill-coverage cost.

## Explicitly deferred (not fixed here)

The ~5.64s average per scoped mutant, once integration-test cost is
removed, is still real and still the largest remaining cost. It is mostly
mutate4py's own per-mutant Python-level orchestration overhead, not purely
subprocess/interpreter-restart cost. No code changes were made for this —
flagging it as a future item only, per explicit scope decision, not a
current recommendation. If it's tackled, the lead is "why does the
per-mutant loop cost ~3.5-4.5s beyond the actual test subprocess," not "add
a persistent test runner" (that would only address the interpreter-startup
slice, which is the smaller part of the ~5.64s).
