# Glossary

Vocabulary used consistently (bold, capitalized) across `docs/spec.md`, the ADRs,
and issue tickets. When a term appears bold in those documents, this is the
definition it refers to. New terms are added here as they're introduced, not
redefined ad hoc in the document that happens to need them first.

- **Baseline** — the once-per-run execution of `--test-command` (or the
  test-executor's default argument list) against unmutated source. It must pass;
  its duration sets `timeout = max(1s, timeout-factor × baseline)` for every
  Mutant in the run (spec §7 step 7).

- **Manifest** — the per-function hash record (`ast.dump()`-based) that makes a
  rerun differential: unchanged functions are skipped once a Manifest exists.
  Stored either as an in-source footer or, with `--manifest-file`, a sidecar
  `<file>.manifest.json` (spec §5).

- **Mutant** — one applied mutation at one Site, run through to a classification
  (`killed`, `survived`, or `timeout`, folded into `killed`). The unit the Run
  loop iterates over.

- **Mutation Report** — the final summary block printed once per run: Killed /
  Survived / Uncovered counts, the `Test selection:` line when `--test-contexts`
  is supplied (ADR 0018), and the Survivors list (spec §8).

- **priming-depth** — how much of the test framework's bootstrap a test-executor
  runs once at prime time versus repeats per Mutant. The forking executor's
  current priming depth is a full `pytest --collect-only` pass: every
  `conftest.py` is imported and whatever framework setup collection triggers
  (e.g. `django.setup()`) runs, once, before the first fork. A shallower priming
  depth — import pytest without running its configuration/collection, so
  framework bootstrap never happens at all before a mutant-specific run — is an
  open, unmeasured question (ADR 0019; follow-up tracked in issue #44).

- **Run loop** — the single orchestration path (spec §7) that discovers Sites,
  selects the ones to mutate, runs the Baseline, then dispatches every selected
  Mutant to completion and prints the Mutation Report. One Run loop regardless of
  Worker count or which test-executor a Worker holds (ADR 0019).

- **Selection outcome** — the per-Site classification `--test-contexts` produces
  before that Site's Mutant is dispatched: `narrowed` (named tests cover the
  line — only those run), `static` (the line is covered only by coverage.py's
  empty/whole-run context — the full argument set runs), or a disagreement
  (`line-absent` / `file-absent` — the run aborts, exit 2, no Mutation Report).
  Exactly three cases, no silent fallback (ADR 0018). A Selection outcome decides
  a Mutant's argument list; it does not decide which Worker runs it or which
  test-executor that Worker holds (ADR 0019).

- **Site** — one discovered mutation location: an operator, boolean, or `0`/`1`
  literal at a specific `(line, column)`, attributed to an enclosing function by
  line range (spec §4). Sites are sorted and assigned a stable index; a Mutant is
  one Site with its mutation applied.

- **test-executor** — the primed-once, run-many abstraction both the forking and
  subprocess execution models implement: prime once, then given an argument list
  and a timeout, run it and return a classification. Formalized as one interface
  in issue #41 — the Run loop depends only on the interface and never branches on
  which implementation a Worker holds. The name replaces "fork server" project-wide
  (issue #43), since "fork server" named one implementation, not the abstraction
  both implementations share. The two current implementations:
  - the **forking executor** (`_fork_server.py`, backfilled by ADR 0019) — primes
    a `pytest.main()` collect-only pass once, then `os.fork()`s a child per
    Mutant; POSIX-only, requires `os.fork`.
  - the **subprocess executor** (`_cmd.py`) — spawns a fresh interpreter per
    Mutant; the always-correct, no-fast-path fallback on every platform.

- **Test-context db** — the coverage.py SQLite context database (`.coverage`,
  generated by `pytest --cov-context=test`) that `--test-contexts PATH` reads to
  compute each Site's Selection outcome (spec §2, ADR 0018).

- **Worker** — one unit of parallel execution under `--max-workers`. Each Worker
  provisions its own isolated tree copy (clone-per-worker via `uv`, ADR 0015) and,
  since ADR 0019, owns exactly one test-executor, primed once and alive for the
  whole run. A run with one Worker (the default) is the same mechanism at the
  Worker count of one — not a separate serial code path.
