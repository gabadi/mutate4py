# ADR 0018 — `--test-contexts` selection is a declared three-case model, not a silent fallback

- Status: accepted
- Date: 2026-08-06
- Feature: F4 (run loop) / `--test-contexts` [PY]
- Spec: docs/spec.md §2 (`--test-contexts` row), §8 (Mutation Report)
- Issue: #27 (supersedes one decision of #15)

## Context

`--test-contexts <path>` (issue #15, Python-only) narrows each mutant's test run
to the pytest tests that cover the mutated line, read from a coverage.py SQLite
context database (`.coverage`, generated by `pytest --cov-context=test`).

The original implementation had exactly one escape hatch:
`TestContextDB.tests_for_line` returned `None` whenever it found no named test
for the line, and `_build_mutant_command` then ran the full `--test-command`.
That single `None` conflated three genuinely different states:

1. tests cover the line;
2. the line runs at import time (module-level constants, imports, class headers),
   so coverage.py records it only under the **empty** context — the whole-run
   context, which the query deliberately skipped (`if not ctx_str: continue`);
3. the db has nothing at all for the line, or does not contain the file — which
   can only mean the db and the LCOV file disagree, because **selected sites are
   LCOV-covered by construction** (the F3 coverage gate, ADR 0007, runs before
   selection). A db miss is therefore an input defect — a stale db, a path-format
   mismatch, or coverage recorded inside a subprocess that `--cov-context` cannot
   see — never "uncovered code".

State 3 is the damaging one: it silently ran the full suite, produced a normal
`survived`/`killed` verdict, and exited 0. A stale db could quietly degrade every
mutant to a full-suite run — the exact opposite of what the flag is for — with no
signal an agent could act on.

mutate4py is agent-first: agents see the `Mutation Report` block (via
`just mutate`) and the exit code, nothing else. Warning lines on stdout are
invisible to them and carry no weight.

Prior art (verified, primary sources): mutmut, Stryker and PIT all give a
mutant with no covering test a distinct visible status; none silently falls back
to the full suite. Stryker's `perTest` coverage analysis runs the full suite for
"static" mutants it cannot attribute to a single test — exactly state 2.
mutmut hard-errors with an actionable message when its test↔mutant mapping breaks
entirely — the generalization of state 3. cosmic-ray and cargo-mutants do no test
selection at all, so they offer no guidance here.

## Decision

**No silent fallbacks. Every Mutant gets exactly one declared outcome.
Disagreeing inputs are a hard error, never a silent repair.**

`TestContextDB.tests_for_line` returns `(outcome, node_ids)` instead of
`list[str] | None`, with four outcomes covering the three cases. Both storage
modes (`line_bits` when `has_arcs=0`, `arc` when `has_arcs=1`) classify
identically, and both now *keep* the empty-context row rather than skipping it —
that row is the case-2 signal:

| Outcome | Meaning | Case |
|---|---|---|
| `narrowed` | named contexts cover the line; `node_ids` are their pytest node IDs | 1 |
| `static` | the line was matched only by the empty (whole-run) context | 2 |
| `line-absent` | the file is in the db but no context recorded the line | 3 |
| `file-absent` | the file is not in the db at all | 3 |

A named test always wins over the empty context when both matched the line.

The run loop maps them:

1. **narrowed** — `"{test_command} {node_id}..."` (node IDs shell-quoted), as before.
2. **static** — the full `--test-command` verbatim, as the stated rule, tallied
   separately from case 1.
3. **`line-absent` / `file-absent`** — `_build_mutant_command` raises
   `TestSelectionError`; `run_mutations` prints
   `error: test-context db disagrees with coverage: <file>:<line>: <hint>` to
   **stderr** and returns **2**. The whole run stops; no `Mutation Report` is
   printed. The two outcomes carry different hints, because the db is the only
   place that can tell them apart: `line-absent` points at a stale db,
   `file-absent` at a path-format mismatch or subprocess-recorded coverage.

The db query for a site happens **before** that site's mutant is spliced in, and
the finalize step (`_finalize_source`: restore source, re-embed manifest, remove
`.mutate4py.bak`) runs on the abort path exactly as it does on the parallel-error
path (ADR 0016) — an abort leaves no half-written file.

**Report contract.** Whenever `--test-contexts` is supplied, the `Mutation
Report` block gains one line, directly after `Uncovered:`:

```
Test selection: narrowed <n>, static <k>
```

Inside the report block because that is the only place agents look. The line is
absent when `--test-contexts` is not supplied, so every existing run's output is
byte-for-byte unchanged.

Because `--test-contexts` already forces serial execution
(`_setup_test_context_db`), this is a serial-path-only change; `_workers.py` and
the parallel engine are untouched.

No `NO_COVERAGE`-style mutant status is needed: the coverage gate guarantees a
selected site's line is covered, so "no covering test" is not a reachable state
for a *correct* pair of inputs.

## Consequences

- A stale or path-mismatched context db now fails the run loudly (exit 2) instead
  of silently degrading it to full-suite runs. This is a **behavior change** for
  existing `--test-contexts` users whose db was already stale: what used to pass
  now exits 2 with the reason. That is the intent.
- `narrowed` vs `static` counts are visible per run, so the value the flag is
  actually delivering is measurable rather than assumed.
- Stale-db risk is mitigated by workflow discipline (regenerate `.coverage`
  alongside `lcov.info`; `just check test` does both), not by code.
- Test-order dependencies exposed by narrowing are ruled a test-suite bug, not
  mutate4py's problem.
- Pytest start-up cost per narrowed run is a separate concern, tracked in #25/#26.
- Still open, deliberately out of scope here: `--test-contexts` with
  `--max-workers >= 2` silently forcing serial execution (it is a silent repair of
  the same family this ADR rejects); and the directory/union batch dispatch
  (`_run_files_and_exit`) collapsing every non-zero per-file exit code to 1, which
  makes a case-3 abort indistinguishable from survivors on a multi-file run.
